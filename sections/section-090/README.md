# Section 090: Autogen Rules

Almost every real Pod in a cluster is not a bare Pod at all — it is a Pod *template* buried inside a Deployment, a StatefulSet, a DaemonSet, a Job, or a CronJob. If you write a Kyverno `validate` rule that only ever says `kind: Pod`, does it actually protect the Deployments developers apply every day?

It does — and the mechanism that makes that true is **autogen**. When a rule's `match` block selects `Pod` and nothing else, Kyverno's policy controller quietly clones that rule, rewrites its field paths to reach into `spec.template` (or, for a CronJob, `spec.jobTemplate.spec.template`), and retargets the clone at the Pod-controller kinds. You write one rule; six kinds get protected. This is genuinely one of the most surprising things about Kyverno the first time you see it happen, and it is also one of the most exam-relevant: the KCA expects you to know exactly what autogen produces, where to go looking for it, and how to control it.

---

## What You Will Master

By completing this section, you will acquire the two core competencies every Kyverno policy author needs around autogen:

* **Reading Autogen Output:** How to apply a Pod-matching `validate` rule and inspect the live `ClusterPolicy` object to find the exact autogenerated rules Kyverno produced, understand the field-path rewriting it performs, and prove empirically that a non-compliant Deployment — not just a non-compliant Pod — gets rejected by a rule that only ever mentioned `kind: Pod`.
* **Controlling Autogen's Scope:** How to use the `pod-policies.kyverno.io/autogen-controllers` annotation to restrict which controller kinds receive autogenerated rules (or disable autogen entirely with `none`), and how to reason about the specific situations where autogen silently declines to fire at all — a multi-kind `match`, for instance — versus situations where it fires but produces a rule you didn't expect.
