# Part 1: What Autogen Actually Generates

## Start with a rule that only says "Pod"

Take the simplest possible validation rule: every Pod needs a non-empty `team` label. Nothing in its `match` block mentions Deployments, StatefulSets, or anything else — just `Pod`.

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-team-label
spec:
  validationFailureAction: Enforce
  background: true
  rules:
    - name: check-team-label
      match:
        any:
          - resources:
              kinds:
                - Pod
      validate:
        message: "A team label is required on every Pod."
        pattern:
          metadata:
            labels:
              team: "?*"
```

Apply it exactly as written, with nothing else — no second rule, no annotation —
and then create a Deployment. Not a Pod. A Deployment, which this policy never
mentions. Read the rule name in whatever comes back.

> [!TIP]
> **Try it — a rule that never said "Deployment" rejecting a Deployment**
>
> ```sh
> kubectl apply -f policy.yaml
> kubectl create deployment bad-deploy --image=nginx
> ```
>
> Expect something like:
>
> ```text
> clusterpolicy.kyverno.io/require-team-label created
>
> error: failed to create deployment: admission webhook "validate.kyverno.svc-fail" denied the request:
>
> resource Deployment/default/bad-deploy was blocked due to the following policies
>
> require-team-label:
>   autogen-check-team-label: 'validation error: A team label is required on every Pod. rule autogen-check-team-label failed at path /spec/template/metadata/labels/team/'
> ```
>
> The rule name is `autogen-check-team-label`, not `check-team-label`. You never
> wrote a rule called that, and the path it failed at —
> `/spec/template/metadata/labels/team/` — is not the path your pattern named
> either.

Kyverno wrote that rule, automatically, the moment you applied a policy whose rule matched only `Pod`. That is autogen: your one rule quietly became several, each retargeted at a kind that carries a Pod template, with the field paths rewritten to reach it.

## Finding the generated rule yourself

The error message already tells you a rule named `autogen-check-team-label` exists somewhere, but where does it live? If you go looking under `spec.rules` on the `ClusterPolicy` you applied, you will not find it — `spec` still contains exactly the one rule you wrote. On this Kyverno version (v1.19.1), autogenerated rules live in a separate part of the object entirely: `status.autogen.rules`.

The quickest way to see both generated rules and what each one covers is to ask
for just their names and target kinds rather than reading the whole object:

> [!TIP]
> **Try it — find the rules you did not write**
>
> ```sh
> kubectl get clusterpolicy require-team-label \
>   -o jsonpath='{range .status.autogen.rules[*]}{.name}{" -> "}{.match.any[0].resources.kinds}{"\n"}{end}'
> ```
>
> Expect something like:
>
> ```text
> autogen-check-team-label -> ["apps/v1/DaemonSet","apps/v1/Deployment","batch/v1/Job","apps/v1/ReplicaSet","v1/ReplicationController","apps/v1/StatefulSet"]
> autogen-cronjob-check-team-label -> ["batch/v1/CronJob"]
> ```
>
> Two rules from your one, split by shape: six kinds that all hold a Pod template
> at `spec.template` share one rule, and CronJob gets its own.

The full objects, with the rewritten patterns, are in the same place:

```bash
kubectl get clusterpolicy require-team-label -o yaml
```

```yaml
spec:
  background: true
  rules:
  - match:
      any:
      - resources:
          kinds:
          - Pod
    name: check-team-label
    validate:
      message: A team label is required on every Pod.
      pattern:
        metadata:
          labels:
            team: ?*
  validationFailureAction: Enforce
status:
  autogen:
    rules:
    - match:
        any:
        - resources:
            kinds:
            - apps/v1/DaemonSet
            - apps/v1/Deployment
            - batch/v1/Job
            - apps/v1/ReplicaSet
            - v1/ReplicationController
            - apps/v1/StatefulSet
        resources: {}
      name: autogen-check-team-label
      validate:
        message: A team label is required on every Pod.
        pattern:
          spec:
            template:
              metadata:
                labels:
                  team: ?*
    - match:
        any:
        - resources:
            kinds:
            - batch/v1/CronJob
        resources: {}
      name: autogen-cronjob-check-team-label
      validate:
        message: A team label is required on every Pod.
        pattern:
          spec:
            jobTemplate:
              spec:
                template:
                  metadata:
                    labels:
                      team: ?*
```

> [!NOTE]
> If you've read older Kyverno material, this may not be what you expect. In older Kyverno releases, the autogenerated rules were spliced directly into `spec.rules` alongside the rule you wrote, so `kubectl get clusterpolicy -o yaml` showed them mixed in with your own. On v1.19.1, `spec.rules` stays exactly as you wrote it — untouched — and everything autogen produced is computed separately and reported under `status.autogen.rules`. The engine still evaluates those generated rules against incoming Deployments, Jobs, and so on; they just aren't stored back into the spec you authored. If a rule name in a rejection error doesn't exist anywhere in your `spec.rules`, `status.autogen.rules` is where to look next.

Two rules were generated from your one rule, not one — and they're grouped differently on purpose:

1. **`autogen-check-team-label`** covers `DaemonSet`, `Deployment`, `Job`, `ReplicaSet`, `ReplicationController`, and `StatefulSet` together, because all six share the exact same shape: a `spec.template` field holding a full Pod template. Your original pattern (`metadata.labels.team`) gets rewritten to `spec.template.metadata.labels.team` and reused as-is across all six kinds.
2. **`autogen-cronjob-check-team-label`** covers `CronJob` on its own, with a differently-rewritten pattern: `spec.jobTemplate.spec.template.metadata.labels.team`. A CronJob doesn't hold its Pod template at `spec.template` — it holds a `jobTemplate` (itself a Job spec) one level further down, so the path rewrite has to reach one level deeper than it does for the other six kinds. That structural difference is exactly why CronJob gets its own generated rule instead of being folded into the first one.

## Proving the same rule protects a Deployment, and only rejects what it should

You already saw `bad-deploy` rejected. Two boundary cases remain, and together
they show that the original rule and its generated clone are genuinely separate
rules that fire on different objects: a bare non-compliant Pod, and a fully
compliant Deployment.

> [!TIP]
> **Try it — which rule name fires depends on what you submitted**
>
> ```sh
> kubectl run bad-pod --image=nginx --restart=Never
>
> kubectl apply -f - <<'EOF'
> apiVersion: apps/v1
> kind: Deployment
> metadata:
>   name: good-deploy
> spec:
>   replicas: 1
>   selector:
>     matchLabels:
>       app: good-deploy
>   template:
>     metadata:
>       labels:
>         app: good-deploy
>         team: platform
>     spec:
>       containers:
>         - name: app
>           image: nginx
> EOF
> ```
>
> Expect something like:
>
> ```text
> resource Pod/default/bad-pod was blocked due to the following policies
>
> require-team-label:
>   check-team-label: 'validation error: A team label is required on every Pod. rule check-team-label failed at path /metadata/labels/team/'
>
> deployment.apps/good-deploy created
> ```
>
> The bare Pod was rejected by `check-team-label` — your rule, at
> `/metadata/labels/team/`. The Deployment was admitted because its label sits at
> `spec.template.metadata.labels`, exactly where the *generated* rule's rewritten
> pattern looks. You never wrote that path anywhere.

> [!NOTE]
> Autogen only ever fires for rules whose `match` selects `Pod`. A rule matching `Deployment` directly is never autogenerated into anything else — autogen is specifically the "Pod rule reaches upward into controllers" direction, never the reverse.
