# Part 2: Controlling Autogen's Scope

Part 1 established what autogen produces when you leave it alone. This part is about telling it to produce less — restricting which controller kinds get a generated rule, or switching it off entirely — and about the consequence that restriction does *not* have.

## The mechanism: an annotation on the ClusterPolicy

Part 1 showed the default behavior: a Pod-only rule gets cloned across `DaemonSet`, `Deployment`, `Job`, `ReplicaSet`, `ReplicationController`, `StatefulSet` (one generated rule) and `CronJob` (a second generated rule, because its Pod template sits one level deeper). You control which of those kinds actually receive a generated rule with a single annotation on the policy itself: `pod-policies.kyverno.io/autogen-controllers`.

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-team-label-scoped
  annotations:
    pod-policies.kyverno.io/autogen-controllers: Deployment
spec:
  validationFailureAction: Enforce
  background: true
  rules:
    - name: check-team-label
      match:
        any:
          - resources:
              kinds:
                - Pod
      validate:
        message: "A team label is required on every Pod."
        pattern:
          metadata:
            labels:
              team: "?*"
```

> [!NOTE]
> This module's brief asked us to verify, rather than assume, whether this annotation is still the live mechanism on a current Kyverno release — older features have a way of migrating into a dedicated `spec` field over time. On v1.19.1, `kubectl explain clusterpolicy.spec --recursive` shows no autogen-scoping field anywhere in `spec` (there is a `spec.rules[].skipBackgroundRequests` boolean, but that only controls background-scan requests and has nothing to do with which controller kinds get autogenerated rules). The `pod-policies.kyverno.io/autogen-controllers` annotation, confirmed against the current Kyverno docs and by testing it directly against a live cluster below, remains the current mechanism.

Applying the scoped policy above and inspecting `status.autogen` shows exactly one generated rule now, for `Deployment` only:

```bash
kubectl apply -f policy.yaml
kubectl get clusterpolicy require-team-label-scoped -o yaml
```

```yaml
status:
  autogen:
    rules:
    - match:
        any:
        - resources:
            kinds:
            - apps/v1/Deployment
        resources: {}
      name: autogen-check-team-label
      validate:
        message: A team label is required on every Pod.
        pattern:
          spec:
            template:
              metadata:
                labels:
                  team: ?*
```

No `CronJob` rule, no `Job` rule, no `StatefulSet` rule — only what you named in the annotation.

## Scoping doesn't mean "unprotected" — it means "protected differently"

Apply that same scoped policy (Deployment only) and create a non-compliant Job:

```bash
kubectl create job bad-job --image=nginx -- /bin/true
# job.batch/bad-job created
```

The Job itself is admitted — `autogen-controllers: Deployment` means no rule was ever generated for `Job`, so nothing intercepts the `Job` object at creation. But look at what happens next:

```bash
kubectl get events --field-selector involvedObject.name=bad-job
# Warning   FailedCreate   job/bad-job   Error creating: admission webhook "validate.kyverno.svc-fail" denied the request: ...
# Warning   FailedCreate   job/bad-job   Error creating: admission webhook "validate.kyverno.svc-fail" denied the request: ...
# Warning   FailedCreate   job/bad-job   Error creating: admission webhook "validate.kyverno.svc-fail" denied the request: ...
```

The Job controller keeps trying to create the actual Pod the Job needs to run — and that Pod submission is a bare `kind: Pod` admission, which your *original* rule (`check-team-label`, not an autogen clone) still matches directly, scoping annotation or no scoping annotation. The Job resource is admitted; the Pod it needs in order to actually do anything never is. The Job sits there failing forever.

> [!NOTE]
> Kyverno actually warns you about exactly this the moment you apply a scoped policy: `Warning: Policies that match Pods apply to all Pods including those created and managed by controllers excluded from autogen. Use preconditions to exclude the Pods managed by controllers which are excluded from autogen.` Restricting `autogen-controllers` only changes which *controller objects* (Deployment, Job, CronJob, …) get their own generated rule — it never narrows what your original Pod rule matches. Any bare Pod, no matter who created it, is still evaluated by the rule you wrote. If you genuinely want Jobs to be exempt end-to-end, you need a `preconditions` block that excludes Pods owned by a Job, not just a narrower `autogen-controllers` value.

## Turning autogen off completely

Setting the annotation to `none` disables autogen entirely — no generated rules at all, for any controller kind:

```yaml
metadata:
  annotations:
    pod-policies.kyverno.io/autogen-controllers: none
```

```bash
kubectl get clusterpolicy autogen-none -o yaml
# status:
#   autogen: {}

kubectl create deployment bad-deploy-none --image=nginx
# deployment.apps/bad-deploy-none created
```

With autogen off, only the literal rule you wrote is evaluated — a Pod-matching rule protects Pods and nothing else. `status.autogen` is empty (`{}`), which is the fastest way to confirm from the command line that a policy has no generated rules at all, whether that's because you disabled it deliberately or because of one of the two situations below.

## Seeing the scoping and its consequence in one run

Everything in this part comes together in a single sequence: narrow autogen to
`Deployment`, confirm the generated rule list shrank, then submit both a
Deployment and a Job and watch them take completely different paths.

> [!TIP]
> **Try it — scoped autogen, and the Job that goes nowhere**
>
> ```sh
> kubectl apply -f scoped-policy.yaml
> kubectl get clusterpolicy scoped-autogen \
>   -o jsonpath='{range .status.autogen.rules[*]}{.name}{" -> "}{.match.any[0].resources.kinds}{"\n"}{end}'
>
> kubectl create deployment bad-deploy --image=nginx
> kubectl create job bad-job --image=nginx
> kubectl get events --field-selector involvedObject.name=bad-job
> ```
>
> Expect something like:
>
> ```text
> autogen-check-team-label -> ["apps/v1/Deployment"]
>
> scoped-autogen:
>   autogen-check-team-label: 'validation error: A team label is required on every Pod. rule autogen-check-team-label failed at path /spec/template/metadata/labels/team/'
>
> job.batch/bad-job created
>
> 11s   Warning   FailedCreate   job/bad-job   Error creating: admission webhook "validate.kyverno.svc-fail" denied the request: ...
> 9s    Warning   FailedCreate   job/bad-job   Error creating: admission webhook "validate.kyverno.svc-fail" denied the request: ...
> 5s    Warning   FailedCreate   job/bad-job   Error creating: admission webhook "validate.kyverno.svc-fail" denied the request: ...
> ```
>
> One generated rule instead of two, covering only `Deployment`. The Deployment
> is rejected outright. The Job is *accepted* — and then fails forever, retrying
> every few seconds, because the Pod its controller keeps trying to create is a
> bare Pod submission that your original rule still governs.

Check for the Job's Pods and you will find none: `kubectl get pods -l job-name=bad-job`
returns nothing at all. The Job object exists, its controller is working, and
nothing it produces survives admission. Clean it up with
`kubectl delete job bad-job` before the event log fills up.

This is the shape of the mistake worth remembering: scoping autogen changes which
*controller objects* get their own generated rule. It never narrows what the
original Pod rule matches, so narrowing the scope does not create an exemption —
it moves the rejection from a place where someone sees it immediately to a place
where they have to go looking for it.

## Section recap

The `pod-policies.kyverno.io/autogen-controllers` annotation restricts which controller kinds receive a generated rule, and `none` disables generation entirely so `status.autogen` comes back empty. Narrowing it is not an exemption: the original Pod-matching rule still governs every bare Pod submission, so a controller left out of scope has its objects admitted and its Pods rejected — moving the failure from somewhere a developer sees it immediately to somewhere they have to go looking.
