# Question

Solve this question against the `kind` cluster provisioned for this lab (Kyverno is already installed and running in the `kyverno` namespace). This capstone combines this section's techniques with the annotation-based control you learned in Part 2.

Write and apply a `ClusterPolicy` that:

1. Has `validationFailureAction` set to `Enforce`.
2. Has a single rule whose `match` block selects **only `kind: Pod`**, requiring every Pod to carry a non-empty `team` label.
3. Carries the `pod-policies.kyverno.io/autogen-controllers` annotation set so that **only `Deployment`** receives an autogenerated rule — `Job`, `CronJob`, `DaemonSet`, `StatefulSet`, `ReplicaSet`, and `ReplicationController` must **not** receive one.
4. Is not restricted to a single namespace; it must apply cluster-wide.

When you're done, the policy must produce exactly this behavior:

- A bare non-compliant Pod is rejected (your rule always governs Pods directly, regardless of the annotation).
- A non-compliant Deployment is rejected (autogen still covers `Deployment`).
- A compliant Deployment is admitted.
- A non-compliant **Job** is admitted at the Job level — the `Job` object itself is not rejected, because `Job` was excluded from autogen scope. (Its underlying Pod may still fail to actually start, since your original Pod rule still governs bare Pods — that's expected, and covered in Part 2 of the module.)
- A non-compliant **CronJob** is likewise admitted at the CronJob level, for the same reason.

You may name the policy and its rule however you like.
