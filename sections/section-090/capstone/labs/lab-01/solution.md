# Solution Guide: Autogen Rules Capstone

One `ClusterPolicy`, one Pod-only rule, and an `autogen-controllers` annotation that narrows the generated rules to `Deployment` alone.

---

## Step 1: Write the policy

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-team-label-scoped
  annotations:
    pod-policies.kyverno.io/autogen-controllers: Deployment
spec:
  validationFailureAction: Enforce
  background: true
  rules:
    - name: check-team-label
      match:
        any:
          - resources:
              kinds:
                - Pod
      validate:
        message: "A team label is required on every Pod."
        pattern:
          metadata:
            labels:
              team: "?*"
```

```bash
kubectl apply -f policy.yaml
kubectl get clusterpolicy require-team-label-scoped -o yaml
```

Under `status.autogen.rules` you should see exactly one generated rule, matching only `apps/v1/Deployment` — no `Job`, `CronJob`, `DaemonSet`, `StatefulSet`, `ReplicaSet`, or `ReplicationController` entry anywhere.

---

## Step 2: Why the annotation, and why this doesn't leave Jobs "unprotected" in the way you might assume

- **`pod-policies.kyverno.io/autogen-controllers: Deployment`** is the only mechanism on this Kyverno version for scoping which controller kinds get a generated rule — there is no equivalent `spec` field. Leaving it unset gives you the default seven kinds; setting it to `none` disables autogen completely; naming specific kinds (comma-separated for more than one) restricts it to exactly those.
- Excluding `Job` and `CronJob` from the annotation does **not** exempt Pods created by a Job or CronJob from your rule. Your rule still says `match: kind: Pod`, and that match is never touched by the annotation — it only controls which *additional*, generated rules exist for controller objects. A `Job` object is admitted freely (no generated rule intercepts it), but the moment the Job controller tries to create the actual Pod it needs, that bare Pod submission hits your original rule directly and gets rejected. The Job succeeds at being created; it then fails forever to actually run anything.

---

## Step 3: Prove all five scenarios by hand

```bash
# 1. Bare non-compliant Pod -> rejected by the original rule
kubectl run bad-pod --image=nginx --restart=Never
# Error ... check-team-label failed at path /metadata/labels/team/

# 2. Non-compliant Deployment -> rejected by the autogenerated rule (Deployment is in scope)
kubectl create deployment bad-deploy --image=nginx
# error: ... autogen-check-team-label failed at path /spec/template/metadata/labels/team/

# 3. Compliant Deployment -> admitted
kubectl apply -f - <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: good-deploy
spec:
  replicas: 1
  selector:
    matchLabels: { app: good-deploy }
  template:
    metadata:
      labels: { app: good-deploy, team: platform }
    spec:
      containers:
        - name: app
          image: nginx
EOF
# deployment.apps/good-deploy created

# 4. Non-compliant Job -> the Job object itself is admitted (Job is NOT in autogen scope)
kubectl create job bad-job --image=nginx -- /bin/true
# job.batch/bad-job created
kubectl get events --field-selector involvedObject.name=bad-job
# FailedCreate events — the Job's underlying Pod is still rejected by check-team-label directly
kubectl delete job bad-job --ignore-not-found

# 5. Non-compliant CronJob -> the CronJob object itself is admitted (CronJob is NOT in autogen scope)
kubectl apply -f - <<'EOF'
apiVersion: batch/v1
kind: CronJob
metadata:
  name: bad-cronjob
spec:
  schedule: "*/5 * * * *"
  jobTemplate:
    spec:
      template:
        spec:
          containers:
            - name: app
              image: nginx
          restartPolicy: Never
EOF
# cronjob.batch/bad-cronjob created
kubectl delete cronjob bad-cronjob --ignore-not-found
```

The grading script exercises all five cases directly against the API server. A policy that used the *default* autogen scope (no annotation, or an annotation naming more than just `Deployment`) would fail check 4 and/or 5, because the Job or CronJob object itself would be rejected outright instead of being admitted with a failing Pod underneath it — that's the specific, testable difference the annotation makes.
